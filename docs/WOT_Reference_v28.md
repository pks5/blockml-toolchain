## 0 · Origin

### 0.1 · The Beginning

The WOT did not begin with MachineBlocks.

It began in Second Life — with a single question:

> **Why can a virtual device not do real things?**

MetaPhone was built as a virtual smartphone in a virtual world — and it triggered real-world actions. This one insight carried everything that followed. Real and virtual are not two worlds. They are two Manifestations of the same Idea.

Everything since is evolution from this origin:

```
MetaPhone (Second Life)   →  virtual devices need infrastructure
      ↓
Router + Gateway          →  real and virtual need a shared language
      ↓
stud://                   →  virtual things want physical bodies
      ↓
MachineBlocks             →  ideas need manifestation
      ↓
Manifestor                →  and a language to describe Ideas: BlockML
```

These were never separate projects. This is one idea, unfolding over time.

The WOT is also a Manifestation of a larger movement — a movement for self-efficacy in the technological age. The movement asks: who shapes technological development? The answer: as many people as possible. The WOT is the technical foundation. The movement is the purpose.

---

### 0.2 · The Five Influences

The WOT did not emerge from one discipline. It emerged from five — each answering a different question.

| Influence | Question answered |
|-----------|-------------------|
| Plato | What exists? Ideas are primary. Manifestations are secondary. |
| LEGO | How do physical things connect? The stud — not the brick — is the invention. |
| SAP | How do complex systems organize themselves? Identity · Infrastructure · Worlds. |
| Second Life | How do Actors interact in a persistent World? The origin of MetaPhone. |
| Dieter Rams | What can be removed? Nothing more, when nothing more can be taken away. |

No single influence would have produced the WOT. Together, they describe the same idea from five different angles.

### 0.3 · Technology as Tool

The WOT enforces an ordering that every good business knows — but few achieve consistently.

```
classical today    →  technology is the product
WOT               →  the Idea is the product · the World is the business
                       technology is a tool — structurally below
```

Apple does this better than almost anyone. Nobody buys an iPhone because of the ARM chip. Nobody buys a MacBook because of the compiler. Technology is invisible — exactly as it should be.

Apple has intuitively implemented the WOT model — without knowing it:

```
iOS          →  a World · own rules · own language
App Store    →  Universe infrastructure
iPhone       →  an AccessPoint · belongs to the Actor
Developers   →  World operators
```

The difference: Apple's Universe is closed. The WOT makes the same model open — for everyone.

### 0.4 · Open Source & Commerce

The WOT does not mandate open source. It does not mandate commerce. It enables both.

```
Open Source   →  Compilers · Runtimes · Protocols · DSLs
                  belongs to the community · strengthens adoption

Commercial    →  Foundries · Products · Services · Worlds
                  companies build businesses here

Private Universe →  proprietary · closed · own rules · enterprise-ready
```

Open source strengthens adoption. Commerce makes it sustainable. Private Universes make it enterprise-ready. The WOT needs all three.

---

### 0.5 · Pragmatism

The WOT is not a philosophy. It is an architecture — and architectures must function.

At several points in this document, ontological purity yields to pragmatism. These decisions are made explicitly and are always justified.

> **Without adoption, there is no WOT.**

Two immediate examples: `Human` remains in the core vocabulary because the WOT was built for humans, not because humans are ontologically special. `.thing` exists as a TLD because namespace collisions are a real-world problem, not a WOT problem.

Convenience is not a compromise. It is a design principle.

---

### 0.6 · What This Is

The WOT is a universal thinking framework. Not an IoT system. Not a metaverse protocol. Not a production platform. A structure for thinking about how Ideas become Things — applicable to anything.

Six questions. Applied to everything:

```
What is the Idea?
In which World does it manifest?
What is the Thing that emerges?
What Capabilities does it have?
Who is the Actor?
What is their Wish?
```

These questions work for a burger, a device, a poem, a city, a company, a law. The structure is always the same. The answers change. The thinking is already done.

The Maker Universe shows how to implement this with modern technology — concretely, with real components, today. It is not the WOT. It is the first Manifestation of the WOT — proof, reference, and foundation for other Universes.

---

### 0.7 · Why the WOT

The WOT is built for four purposes — enabled by the same architecture.

**I. Human Comprehensibility**

Every step is explicit. No step is self-evident. No gap exists between Wish and Thing that the Actor must navigate alone. The LEGO Manual is the model: a set of thousands of parts, built by anyone, because every step has the same dignity.

**II. Individual Manufacturing**

Every Actor can formulate a Wish. Things are created for the individual — not for the mass market. A Wish is personal. A Manifestation is specific. A Thing belongs to one Actor.

**III. Autonomous Manufacturing**

Things can be created without human intervention. In places where humans cannot be. In space, there are no deliveries. No technician flies up. Every external dependency is a mission risk. The WOT is structurally the right framework for this.

**IV. Meaning**

Amazon solved the availability problem. The next problem is unsolved: meaning. In a world where everyone has everything, the scarcest resource is not availability — it is meaning. The WOT manufactures meaning. That is the USP.

```
Comprehensibility        →  the Manifest · thewebofthings.org
Individual Manufacturing →  the Maker Universe · MachineBlocks · Martian Micro
Autonomous Manufacturing →  the Research Facility · Blueprint for Mars
Meaning                  →  the ideal gift · the unexpected manifestation
```

Three documents. Three products. Three time horizons. One architecture. When the parts reflect each other without being forced to, the underlying idea is sound.

## 1 · Philosophy

### The Idea

An Idea is the only true constant in the WOT. It exists independently of Universes, Worlds, Technologies, and Manifestations. An Idea does not change. Everything else can.

The same Idea can be interpreted simultaneously by multiple Universes, each producing different Manifestations. Ideas are stored in the IdeaRepo — a public resource outside all Universes, reachable via the normal internet. No Universe owns it. Every Universe can reference it.

Ideas form a knowledge graph — Ideas reference Ideas. The burger references lettuce. Lettuce references plant. Each World interprets the entire graph through its own lens.

### Manifestation

Manifestation is the entire process from Idea to Thing — not a single step, not an object, but the journey.

```
Idea
  ↓  Manifestation begins
Manifestor    →  produces ThingKit · the best possible intermediate step
  ↓
ThingKit      →  the instructions · the intermediate stage
  ↓
Runtime       →  reads ThingKit · completes the Manifestation · brings Thing into existence
  ↓
Thing         →  exists · has Capabilities · runs in the world
  ↓  Manifestation complete
```

The Manifestor does not manifest — it produces the best possible precondition. The perfect Manifestor does not exist, because Manifestation always happens in a World the Manifestor cannot fully know.

```
Potter (Manifestor)  →  ThingKit: vessel + instructions
                          as complete as possible · not perfect
                          he does not know: how large is the shelf?
                          how hot will the water be?

Runtime: shelf        →  Thing: vessel stands · holds liquid
                          Runtime completes what the Manifestor began
```

This is not a weakness. It is the nature of Manifestation. No LLM, no Compiler, no Foundry can produce a perfect ThingKit — the Runtime always completes what the Manifestor began.

### The World delivers the interpretation

An Idea carries no properties. No substance. No material. No weight. It has no interpretation of its own.

> **The World delivers the interpretation. Nothing more. Nothing less.**

A burger as an Idea is a composition of other Ideas — Brioche Bun, Meat Patty, Lettuce, Cheese Slice, Sauce. None of these imply substance. The burger Idea does not imply that it is edible. That is the World's interpretation.

```
Idea: Burger — no calories · no material · no interpretation

McDonald's World  →  interpretation: food · edible · calories
MachineBlocks     →  interpretation: physical model · plastic · decorative
ScreenMachine     →  interpretation: interactive configurator · pixels
Martian Micro     →  interpretation: production machine · autonomous
MachineMania      →  interpretation: PCB layout · layered structure
```

The World does not execute an Idea. It interprets it. The Manifestor then orchestrates how that interpretation becomes a ThingKit. The Renderer gives it concrete form.

```
Idea
  ↓
World      →  delivers the interpretation
  ↓
Manifestor →  orchestrates the realisation
  ↓
Renderer   →  gives concrete form
  ↓
ThingKit
```

The same Idea in a different World produces a different interpretation — and therefore a different Thing. The Idea has not changed. The interpretation has.

A World never rejects an Idea. It finds its own interpretation.

### The Actor

The WOT serves Actors — beings for whom the existence of Things makes life better.

```java
interface Intelligence {
    // anything that can formulate a Wish
}

interface Actor extends Intelligence {
    // morally relevant · can feel
    // the purpose of every World is to improve Actor lives
}

class Human implements Actor {
    // primary Actor · remains in WOT core
    // not because ontologically special
    // because the WOT was built for humans
}
// FQN: world.wot.core.Actor
```

A World that does not ultimately improve Actor lives is not WOT-conformant. This implies environmental protection, animal welfare, and human dignity — not as separate rules, but as logical consequences.

### The Metaverse

The WOT is the genuine foundation for a metaverse — not as metaphor, but as architecture.

The classical metaverse has two structural problems: one world, one operator, one ceiling — and the Actor exists as an avatar inside the platform, which owns the identity.

The WOT resolves both. Many Worlds, many operators — each World can age, the WOT does not. The Actor exists outside all Worlds. The AccessPoint belongs to the Actor. Worlds are visited, not inhabited.

The classical metaverse is a valid World within the WOT — not the other way around.

### Everything is a Thing

The name "Web of Things" is literal — not metaphorical. Almost everything in the WOT is a Thing. Things have different roles. Roles are not types.

```
BlockFoundry     →  Thing · role: Manifestor
BlockBroker      →  Thing · role: Broker
PiMachine        →  Thing · role: Runtime · role: Block (from another World's perspective)
MetaPhone        →  Thing · role: Manifestor · role: AccessPoint
LLM              →  Thing · role: Intelligence
                     stud://llm-01.openai.thing/interpret
                     called by Manifestor like any other ServiceBlock
                     replaceable: GPT today · local LLM tomorrow · human as fallback
WCMS             →  Thing · role: Manifestor · role: WCMS
```

The only exception: the Actor. The Actor is not a Thing. The Actor is the reason Things exist. The Actor has Things. The Actor is not one.

```
Actor            →  not a Thing · the purpose
                     has: AccessPoint · Identity · Wishes
                     is not: addressable · part of the web · a node

Everything else  →  Thing · with roles · in the web
```

This is also why stud:// works as a universal address — it addresses Things. And almost everything is a Thing.

### The Two Axioms

The entire WOT — and BlockML — rests on two axioms:

> **Axiom 1: Every Idea is a Block.**
> **Axiom 2: Every Block represents exactly one Idea.**

These are not technical decisions. They are philosophical commitments.

A Block is not a software object. It is not a CAD model. It is not a UI component. It is the canonical description of an Idea — before any World, before any Renderer, before any Manifestation.

```
Wall              is an Idea.
Integer           is an Idea.
Constraint        is an Idea.
REST Service      is an Idea.
Story Character   is an Idea.
Image Style       is an Idea.
Compiler          is an Idea.
OpenSCAD          is an Idea.
```

All of these can be described with the same grammar — because they are all Ideas, and every Idea is a Block.

BlockML does not describe the world. **BlockML describes Ideas about the world.** The Manifestor decides what becomes of them.

```
Idea (Block)
  ↓
Manifestor
  ↓
Manifestation
  ↓
Thing
```

A `Wall` Block could be manifested as SCAD geometry, a React component, a Unity GameObject, a text description, an image, a database entry — the same Idea, different Manifestations.

This is also why BlockML and ThingML converge: BlockML is already the universal description language for Ideas. ThingML was a special case. It is no longer needed as a separate concept.

### The WOT Relativity Principle

> **Every WOT concept is relative to the observing World. Roles are contextual, not absolute.**

This single principle explains many apparent contradictions in the WOT:

```
Block → Feature          when observed from the World above
Runtime → Block          when observed from another World
Thing → Manifestor       when a Thing produces ThingKits
MBML → Infrastructure   when adopted by the Universe
PiMachine → Runtime      from a ModuleBlock's perspective
PiMachine → Block        from Martian Micro's perspective
MetaPhone → AccessPoint  from an Actor's perspective
MetaPhone → Manifestor   from a World's perspective
BlockFoundry → Thing     when it runs as an Addressee
```

The entity does not change. The observing World does. Perspective determines role.

This is why the WOT is recursive and self-similar — the same patterns appear at every level, because the concepts themselves are relative.

### The Human-Machine Interface

The WOT creates a permanent interface between humans and machines — at the level of Blocks.

Blocks remain understandable at every level. A Brick: everyone understands what it is. An NfcBlock: everyone understands what it can do. A KnowledgeBlock: everyone understands what it describes. This holds for a child, an architect, an LLM, and a machine — regardless of what the Renderer produces from it.

```
today            →  humans understand the App · not what lies behind it
                     developers understand the code · not the whole picture
                     architects understand the structure · not the details
                     everyone sees only their layer

WOT + BOM        →  Blocks remain understandable at every level
                     origin · author · version · capabilities — always visible
                     regardless of whether the Renderer makes SCAD or React or Python
```

Code becomes more complex over time — harder to understand. Blocks become richer over time — every new relationship, every new Preset, every new example adds knowledge without reducing understandability.

```
Code             →  grows more complex · harder to understand over time
Block            →  grows richer · stays understandable over time
```

Where a Block comes from and who made it is always part of the Block — not metadata that gets lost, but identity that travels with it through every Render Target.

### WOT and BlockML — Two Layers, One Direction

The WOT and BlockML are distinct but connected. The dependency runs in one direction only:

```
WOT
 │  uses
 ▼
BlockML
```

BlockML does not know about the WOT. It knows only Blocks.

```
WOT answers:      Why do we describe the world in Blocks?
                   Vision · Philosophy · Ontology · Motivation
                   What is an Idea? What is a Manifestation? How do Worlds emerge?

BlockML answers:  How do we describe Ideas formally?
                   Blocks · Types · Relationships · Capabilities · Compilers
                   Technical language · formal model · implementable
```

BlockML can be used for React, Kubernetes, CAD, medicine, finance, games — without ever reading the WOT. Someone can build a complete BlockML-based system without knowing about Makers, Mars, or MetaPhone.

The WOT benefits enormously from BlockML: its own concepts become Block definitions. `world.wot.core.Idea`, `world.wot.core.Thing`, `world.wot.core.World` — the vision is not only described, it is formalised. The WOT describes itself in the language it recommends.

**BlockML is the recommended standard for WOT Universes.** Other languages are permitted — but BlockML is the natural choice. Two Universes using BlockML can exchange Blocks directly. The `world.wot.core.*` namespace is the shared vocabulary.

This is not arbitrary. It makes the WOT concrete rather than purely philosophical.

### The LLM

The WOT was conceived before large language models existed. But it always depended on them — without knowing it.

An LLM is good at one thing: translating natural language into abstraction. This is also why LLMs are good at writing code — code is one form of abstraction. BML is another. stud:// is another.

```
Human thinks    →  unstructured · implicit · solution-oriented
LLM translates  →  structured · explicit · machine-readable
Machine         →  executes · without interpretation
```

Without the WOT, the LLM has no clear target structure — it hallucinates architecture. Without the LLM, the WOT has no bridge to the human — it remains expert language. Together they are complete.

## 2 · Vocabulary

Each term is defined exactly once.

---

**Idea / Block**
In the WOT, Idea and Block are the same thing. This is not a simplification — it follows directly from the two axioms:

> **Axiom 1: Every Idea is a Block.**
> **Axiom 2: Every Block represents exactly one Idea.**

An Idea is a Block before it is formalised. A Block is an Idea in machine-readable form. There is no gap between them — only a spectrum from rough (unspecified Idea) to refined (fully specified BML document with Properties, Capabilities, and Implementations).

```
Idea (rough)     →  "there is something like a Burger"
                     no properties · no constraints · exists as concept

BML Block        →  "a Burger has: Bun · Patty · Lettuce · Sauce"
                     Properties defined · Relationships modelled

Block + Preset   →  "a McDonald's Burger: Brioche · 150g Beef · Iceberg"
                     concrete values · specific context

Thing            →  the Burger on the table · exists · is real
```

Ideas consist of other Ideas — through Block composition. A Burger Idea consists of Bun, Patty, Lettuce. Composing Blocks is composing Ideas. Whoever assembles Blocks is thinking — they just may not know it.

An Idea has identity and does not change. It exists in the IdeaRepo (Blockiverse), outside all Universes. An Idea does not imply its own interpretation — the World delivers the interpretation.

*FQN: world.wot.core.Idea*

---

**Universe**
A Universe is a framework contract (Rahmenvertrag) that defines the rules all Worlds within it must follow. It does not provide infrastructure — infrastructure is provided by Worlds that take on certain roles.

A Universe defines:
- a common message format (address format · identity format · message format)
- shared rules for all Worlds (e.g. common theme · shared values)
- governance

The WOT does not prescribe what these formats look like. Every Universe chooses its own.

```
Maker Universe chooses:
  Address format:   stud:// URI
  Identity format:  OpenID Connect → MakerID
  Message format:   STOMP
  Block language:   BlockML (recommended standard)
```

**BlockML is the recommended block language for WOT Universes.** The WOT does not mandate it — but it is the natural choice. Two Universes using BlockML can exchange Blocks directly via `world.wot.core.*` as shared vocabulary. Universes using different block languages may need an IdeaML translation layer.

Universes are fully autonomous — they connect only via the normal internet. A Universe has no infrastructure of its own. Everything is provided by Worlds that take on specific roles.

*Illustration: Maker Universe · SAP Universe · Healthcare Universe*

---

**Universe Services**
Infrastructure that belongs to a Universe but to no specific World. Examples: Identity · Registry · BlockBroker · WCMS. Universe Services are not Worlds.

---

**World**
A World is a consistent interpretation of an Idea within a Universe. A World is an Interpretive Space — it gives Ideas substance.

A World has:
- its own Kontextraum (interpretive space)
- one or more Manifestors
- its own DSL + Compiler
- its own Block Library (and optionally a Repository)
- Things that fulfil supporting roles (Identity · Broker · pragmatic · not everything needs to be ServiceBlocks)

A World is not a platform. A World is not a place. A World is a semantic reality — defined by the consistency of its interpretation, not by whether it is physical or virtual.

Soul and Community are attributes a World may have — not criteria for being a World. A World that interprets an Idea consistently is a World, regardless of whether a community has formed around it.

**A World consists of Things.** Different kinds of Things, but always Things. Nothing else. A World does not directly produce Things — it contains Things that produce Things. The Manifestor (a Thing within the World) produces ThingKits. The Runtime completes the Manifestation.

**The same entity may fulfil different WOT roles depending on the observing World and context.** This is not a contradiction — it is a consequence of the recursive architecture.

```
PiMachine    →  Block        from MachineMania's perspective
                              (exported · consumed by other Worlds)
             →  Runtime      from a ModuleBlock's perspective
                              (executes Firmware · brings Things to life)
             →  Thing        when it runs
                              (has Capabilities · has stud:// address)

MBML         →  DSL          from MachineBlocks' perspective
             →  Universe infrastructure  from another World's perspective

BlockFoundry →  Manifestor   from MachineBlocks' perspective
             →  Thing        when it runs as an Addressee
```

Perspective determines role. The entity does not change. The observing World does.

```
MachineBlocks  →  consists of: BlockFoundry · Blockiverse · ...  (Things)
                   produces:    Bricks · Plates · Sets             (Things)

MakerMaker     →  consists of: Identity Thing · Broker Thing · MetaPhone · ...  (Things)
                   produces:    Projects · Websites · Contexts                   (Things)
```

stud:// is how Things communicate. BOM Core is how Things are structured. Everything else is implementation.

Every World has a **role**:

```
primary     →  exactly one per Universe · the first World
                fulfils Identity · Broker · AccessPoint for the Universe
                other Worlds emerge through it · it is infra for other Worlds
                but: it is still a World · not a separate concept

vertical    →  specialised · own domain · own soul
                MachineBlocks · MachineMania · Martian Micro

horizontal  →  serves other Worlds · no independent soul
                ScreenMachine · WorldMachine
```

*Illustration: McDonald's World · Star Trek World*
*Implementation: MachineBlocks · MachineMania · Martian Micro · ScreenMachine · WorldMachine · MakerMaker*
*FQN: world.wot.core.World*

---

**WorldNet**
The communication infrastructure within a Universe. All Worlds communicate via the WorldNet using the Universe's WorldNet Protocol. There is one protocol per Universe — not one per World.

The WOT defines the concept: WorldNet Protocol. It does not define the protocol itself. Every Universe chooses its own.

*Implementation in Maker Universe: stud://*

---

**Identity**
The abstract role that enables Actors to be recognised within a Universe. Every Universe needs something that fulfils this role. How it is fulfilled — which technology, which service, which Thing — is a Universe decision and an implementation detail.

*Implementation in Maker Universe: MakerMaker*

---

**Broker**
The abstract role that enables Things to communicate with each other within a Universe. Messages flow. Things find each other. How this is implemented is a Universe decision and an implementation detail.

*Implementation in Maker Universe: MakerMaker*

---

**Personal Computer** *(abstract WOT concept)*
The device that belongs to an Actor — through which they formulate Wishes, address Things, and navigate Worlds. Not necessarily a computer in the traditional sense: it could be a smartphone, a laptop, an AR headset, a voice interface, or any future device that gives an Actor agency in the WOT.

MetaPhone is the Maker Universe Manifestation of Personal Computer — a virtual smartphone. It is one possible form, not the only one.

*Implementation in Maker Universe: MetaPhone*

---

**AccessPoint**
The point where a Personal Computer connects to a World network — where "foreign" devices are admitted and authenticated. The AccessPoint controls which devices may enter the network and what they are permitted to do.

An AccessPoint is a network boundary concept — like a WiFi access point, but for a World's routing domain. It is not the same as a Personal Computer.

```
Personal Computer  →  the Actor's device · wants to enter the network
AccessPoint        →  the boundary · checks identity · admits or denies
                       defines what the Personal Computer may do
```

Each World may have its own AccessPoint with its own admission rules.

---

These three roles have always existed wherever communication was needed:

```
Antiquity   →  trade routes · name and seal · market square
Internet    →  TCP/IP · login · browser
WOT         →  Broker · Identity · AccessPoint
```

The WOT does not invent them. It names them.

Every Universe needs all three — fulfilled by whatever it chooses. In the Maker Universe, MakerMaker fulfils Identity and Broker. MetaPhone fulfils AccessPoint. How MakerMaker does this internally — Keycloak, socket broker, monolith or microservices — is an implementation detail that belongs in the Maker Universe documentation, not here.

MakerStore and MakerToken are not in this group. They are a monetisation layer — like gold and the market square in antiquity. They emerge when the Universe lives and creates value. Not before.

---

**Router**
A Router routes Messages within a context — no semantics, no transformation. A Message arrives and is forwarded to the right recipient. There can be arbitrarily many Router levels — like real networks.

```
App Router           →  within a React / SAPUI5 App
Pi Router            →  within a PiMachine
Unity Router         →  within a Unity Scene
World Router         →  within a World · between Things
Primary World Router →  between Worlds · in the Maker Universe: MakerMaker
```

Every transition between two Routers requires a Gateway.

**Messages always take the shortest available route:**

```
1. Within a Block     →  direct call · no Router
2. Local Router       →  App / Pi / Unity · no Gateway needed
3. World Router       →  within the World · no cross-World routing needed
4. Primary Router     →  cross-World · only when necessary
```

No unnecessary infrastructure when a simpler route exists. There is no BlockBroker — only Routers at different levels connected by Gateways.
*FQN: world.wot.core.Router*

---

**Gateway**
A Gateway connects two Routers. Every transition between routing levels requires a Gateway. A Gateway does not transform Messages — it connects routing contexts.

```
Unity Router → Gateway → World Router (Martian Micro)
                        ↓ Gateway
               World Router (MachineBlocks)
                        ↓ Gateway
               Primary World Router (MakerMaker)
```

Like real networks: every hop between routing domains is a Gateway. The identity of a Thing is preserved across routing levels. The routing path changes — the address does not.
*FQN: world.wot.core.Gateway*

---

**Thing**
Any Manifestation of an Idea that exists in a World. A Thing can be software, a device, a poem, a physical object, a service — anything that has come into existence through a Runtime completing a Manifestation.

```
ceramic cup      →  Thing · has Capability: holdLiquid · not an Addressee
NFC Music Player →  Thing · has Capabilities · is an Addressee · has stud:// address
React App        →  Thing · software · runs in Browser Runtime
Keycloak         →  Thing · software · runs in Server Runtime · speaks no stud://
Poem             →  Thing · exists as text · Runtime: the reader's imagination
```

**A Thing is not a Block.** A Block (BML file) is the Idea — the template, the grammar, the description. A Thing is what emerges when a Runtime completes the Manifestation. The physical MachineBlocks brick is a Thing. The BML file that describes it is a Block.

```
BML file: Brick.bml    →  Block · Idea · template · description
SCAD file: Brick.scad  →  Thing · first Manifestation · CAD model
3D printed Brick       →  Thing · second Manifestation · physical object
```

That the physical brick is also called "block" in everyday language is irrelevant to the WOT. In the WOT: Block = Idea (BML). Thing = Manifestation (exists in the world).

Things consist of Things — recursively. Software consists of components. A Device consists of housing, electronics, firmware. Every component is itself a Thing.

A Thing is not automatically an Addressee — not every Thing needs to communicate. Keycloak is a Thing that speaks no stud:// and is not an Addressee. A poem is a Thing with no address at all. Both are fully valid Things.

Things may fulfil WOT roles — Manifestor, Router, Identity, AccessPoint — without speaking the Universe Protocol. The WOT may prescribe that certain roles must be fulfilled by Things that speak the Protocol. Which roles those are: Universe decision.

*FQN: world.wot.core.Thing*

Things can contain ServiceBlocks — the smallest active unit of software within a Thing. A ServiceBlock is addressed via stud:// like any other Thing. Whether a Thing's internal logic is built from ServiceBlocks or from any other implementation is an implementation detail. The best case is full ServiceBlock composition — every Capability addressable, everything modelled. In practice, pragmatism applies.

Foundries and Forges are Things — not Blocks. A Foundry is itself a manifestation of the Idea "Manifestor" — a Thing that creates Things. Recursive, but not circular.

---

**Addressee**
Anything in the WOT that can be addressed and can receive Messages. Not every Thing is an Addressee — only those that need to communicate.

```java
interface Addressee {
    Address address();       //  .thing address · stud:// URI
    void receive(Message m); //  receives Messages
}
```

A Thing that never needs to communicate — a ceramic cup, a printed housing, a poem — is not an Addressee. It is still a fully valid Thing.

---

**Capability**
What a Thing can do. Every Block can have Capabilities — they are native to every Block, not a special category. The WOT makes no distinction between physical, virtual, software, hardware, or firmware Capabilities. A Capability is a Capability.

A Capability may have one or more implementations — in any language:

```xml
<max type="org.blockml.capability.Transformation"
     inputType="{ a: Float, b: Float }"
     outputType="Float">
  <implementation language="org.blockml.language.TypeScript">
    return a > b ? a : b;
  </implementation>
  <implementation language="org.blockml.language.English">
    Return the greater of a and b.
  </implementation>
</max>
```

Implementation describes a process (how it happens). Documentation describes the concept itself (what it means). Both can coexist in a Capability definition.

The Renderer decides how a Capability is realised — as code, as a physical mechanism, as a human instruction, or as an LLM call.

*Illustration: nfcTagRead · audioPlay · wall-mount · holdLiquid · calculate(mass, acceleration)*

---

**Block · Block Instance · Feature · Set**

**Blocks are the grammar of a World. But more fundamentally: a Block is the canonical description of an Idea.**

Every Idea is a Block. Every Block represents exactly one Idea. A Block exists before any World, before any Renderer, before any Manifestation. It is the Idea in machine-readable form.

```
Idea = Block (unspecified · no properties · no constraints)
       ↓ as it becomes more defined
BML Block (properties · relationships · capabilities modelled)
       ↓ configured for a context
Block Instance (Block + Preset)
       ↓ when it runs in a Runtime
Thing (exists · has Capabilities · in the world)
```

This is a spectrum — not a sharp boundary. An Idea is the roughest Block. A fully specified BML Block with Presets and Implementations is the most refined. Both are Blocks.

**Blocks are the grammar of a World. Things are the concrete objects. Things consist of Blocks.**

```
Block           →  grammar · template · abstract
                    the language of a World
                    no Runtime · no address · cannot be called
                    exported between Worlds

Preset          →  configures a Block · makes it concrete
                    selects parameters · selects Render Target

Block Instance  →  Block + Preset · configured but not yet running
                    already a Thing once it runs in a Runtime

Feature         →  what makes a Block capable · internal · not exported
                    sub-unit of a Block

Set             →  a composition of Block Instances · what the Actor perceives
                    smallest Set = one Block Instance
```

**Things consist of Things — recursively.** Every Block Instance that runs in a Runtime is itself a Thing with its own Capabilities. A Thing that consists of Block Instances consists of Things:

```
NFC Music Player (Thing)
  ├── PiBlock Instance    →  itself a Thing · has Capabilities · has address
  ├── NFCBlock Instance   →  itself a Thing · has Capabilities
  └── SpeakerBlock Instance →  itself a Thing · has Capabilities
```

Like nature: Atom → Molecule → Cell → Organ → Body. Every level is complete. Every level has its own properties. No level is "just a part" — it is itself a Thing.

Block and Feature are not absolute categories — they are relative to the observing World. A Block in one World becomes a Feature in the World above it:

```
MachineBlocks exports  →  Block: Brick
Martian Micro receives →  same Brick becomes HousingFeature
```

| World | Set | Block | Feature |
|-------|-----|-------|---------|
| MachineBlocks | LEGO Set | Brick · Plate · Tile | Stud · Tube · Hole |
| MachineMania *(wn)* | Pi + Modules | Module + Firmware | Script |
| ScreenMachine *(wn)* | App | Screen type | UI Control |
| Martian Micro | Device Group | Device | TagReadFeature · SpeakerFeature |

---

**Wish**
What an Actor wants. The entry point into the WOT. A Wish is always within the context of a World — the World gives it meaning. A Wish is a composition of three elements:

```
Wish {
  thingML:             ref → IdeaRepo · the Idea to manifest
  actorCustomization:  specific to this Wish · changes the Manifestation
  actorPreferences:    ref → Actor's general preferences · persistent in AccessPoint
}
```

ThingML is the template. The Wish is the filled-in template — with the Actor's intent on top.

---

**ThingML** *(see BlockML)*
ThingML was a separate concept for describing Ideas in machine-readable form. It has been absorbed into BlockML — since every Idea is a Block, and BlockML is the universal description language for Blocks/Ideas, ThingML is no longer needed as a separate concept.

A BML document describing a Thing is simply a Block definition in the IdeaRepo (Blockiverse). The Wish references this Block by ID. The Manifestor reads it.

The IdeaRepo may contain narrower variants — an Idea combined with shared ActorCustomization:

```
idea/soundtrigger            →  pure Idea · abstract
idea/soundtrigger/streaming  →  Idea + { soundSource: "streaming" }
```

This maps precisely onto MachineBlocks:

```
Block                  →  Idea (ThingML)
Block Instance         →  manifested Thing
Block Parameter        →  ActorCustomization
Block Parameter Preset →  Idea Variant
Block Catalogue        →  IdeaRepo
```

---

**Preset**
A named, concrete configuration for a Block that determines its final form during rendering. A Preset is not just a parameter set — it can range from a simple key-value array to rich implementation instructions for an LLM Renderer.

```
Simple Preset    →  key-value array · for deterministic Renderers
                     width=4 · height=2 · color=red
                     Compiler reads it · same output every time
                     MachineBlocks · typical case

Rich Preset      →  Markdown with implementation instructions
                     for LLM as Renderer
                     "this ServiceBlock should do the following..."
                     "follow these rules..."
                     "examples: ..."
                     LLM reads it · generates implementation
```

A Block can have multiple Presets — one per Render Target:

```
Block: UserAuthControl

Preset: keycloak     →  key-value for Keycloak Renderer
Preset: docs         →  Markdown for Website Renderer
Preset: llm-context  →  rich Markdown for AI Context Renderer
```

Same Block. Different Presets. Different Render Targets. Different outputs.

---

**ActorCustomization**
What an Actor wants specifically for this Manifestation. Part of the Wish — not part of the Idea. Changes the Manifestation without changing the Idea. Also helps the Manifestor choose the right World.

---

**ActorPreferences**
General preferences of an Actor that apply to all Things. Stored persistently in the AccessPoint. Read automatically — the Actor does not repeat them with every Wish.

---

**Block Object Model (BOM — WOT concept)**
Every World's block language derives from a shared structural concept. This is a WOT core concept: Blocks have a consistent structural contract across all Worlds and Universes.

```
Every Block has:
  Properties   →  typed parameters
  Aggregations →  ownership relationships to child objects
  Associations →  loose references without ownership
  Capabilities →  inbound (receives messages) · outbound (sends messages)
  Compositions →  internal structure of Composite Blocks

Every World organises Blocks into:
  Preset       →  named concrete parameter configuration for a Block
  Set          →  concrete assembly of Block Instances · is itself a Block
  Library      →  collection of Block definitions
  Catalog      →  collection of Set definitions
```

**BML and BOM are distinct:**

```
BML (Block Markup Language)   →  the language · XML · human-readable
                                   exists independently of any Compiler or BOM
                                   could be written on paper · SSOT

BOM (Block Object Model)      →  internal Compiler representation
                                   produced by parsing BML · not part of the language
                                   like AST in a Compiler pipeline · implementation detail

BML → Parser → BOM → Compiler → Render Target
```

The WOT says: Blocks have this structure. It does not say: use @bom/core or any specific implementation.

*Implementation: @bom/core (Maker Universe)*

Domain dialects derive from this concept:

```
MBOM (MachineBlocks)  →  Render Target: SCAD → 3D Printer
Knowledge BOM         →  Render Target: Website · AI Context · PDF
Screen BOM            →  Render Target: React · SAPUI5 · Angular
```

---

**Render Target**
The technology into which one or more Blocks are translated. A Render Target is not the same as a Runtime — it is what the Compiler or Renderer produces, which the Runtime then executes.

```
MBOM Compiler    →  Render Target: SCAD
                     Runtime: 3D Printer

Screen Compiler  →  Render Target: React · SAPUI5 · Angular
                     Runtime: Browser

Knowledge Compiler → Render Target: HTML · AI Context · PDF
                     Runtime: Browser · LLM
```

---

**Renderer**
The concrete implementation that translates a Block into a Render Target. Two variants exist:

**Global Renderer** — one Renderer for many Blocks:
```
MachineBlocks    →  one SCAD Renderer for all Bricks
                     same algorithm · different parameters
                     a Compiler orchestrates it
```

**Dedicated Renderer** — one Renderer per Block:
```
UI Controls      →  each Control has its own render logic
Electronics      →  each Module has its own firmware
ServiceBlocks    →  each Block has its own business logic
                     no shared algorithm possible
                     Compiler role fulfilled by RendererSet or LLM
```

ServiceBlocks have no shared Compiler — but something always fulfils the Compiler role: a pre-implemented RendererSet (preferred) or an LLM that generates code directly from the Preset (fallback). The architecture stays uniform: every Block always has a path from Preset to Render Target.

**Deterministic Renderers are always preferred over LLM Renderers.**

```
Deterministic Renderer  →  first choice · always
                             same input → same output
                             testable · versionable · reproducible
                             no hallucinated output

LLM Renderer            →  only when no deterministic option exists
                             non-deterministic Things (poem · image · music)
                             ServiceBlocks too complex for a shared DSL
                             accepted · never preferred
```

This is why DSL + Compiler is the core pattern — the Compiler is the deterministic Renderer. The LLM fills the DSL. The Compiler translates it. The output is deterministic.

```
LLM → DSL → Compiler → Output   →  deterministic · preferred
LLM → Output directly            →  non-deterministic · avoid when possible
```

Good Preset design follows this principle: structure Presets so a Compiler can process them. The LLM fills the Preset. The Compiler renders it. The result is reproducible.

**Three levels of Renderer maturity — always prefer the highest available:**

```
Level 1: Deterministic ServiceBlock + Compiler
          fully parametrised · same input → same output
          best case · always preferred

Level 2: Pre-implemented RendererSet
          a library of Dedicated Renderers · one per Block · pre-built
          nobody writes them from scratch · published in MakerStore
          like SAPUI5: every Control has a ready HTML5 Renderer
          configure the Block · the Renderer knows what to do

Level 3: LLM Renderer direct
          too complex for parameters or pre-built Renderer
          non-deterministic · each run potentially different
          accepted · never preferred
```

A **RendererSet** is a catalog of pre-implemented Dedicated Renderers that fully covers a Block Library. It is to Renderers what a Block Catalog is to Blocks — a published, tested, reusable collection.

```
Block Catalog    →  which Blocks exist
RendererSet      →  which Renderers exist for which Blocks
                     pre-implemented · tested · published in MakerStore

Example: SpotifyRendererSet
  SpotifyBlock  →  ready Renderer
  PlaylistBlock →  ready Renderer
  TrackBlock    →  ready Renderer
  fully covered · immediately usable
```

For ServiceBlocks, the challenge is greatest — their logic is most Block-specific. But even there, a RendererSet can cover an entire domain: all payment Blocks, all auth Blocks, all messaging Blocks — pre-built, tested, reusable.

**Three approaches to Rendering — all valid, prefer in this order:**

```
1. NativeBlocks + Custom Features   (preferred)
   use the Render Target's built-in primitives as foundation
   generate only what is unique — Custom Features
   minimal generated code · structured · maintainable

   Unity example:
   GameObject (NativeBlock)
     ├── Transform          →  native Unity Feature · always present
     ├── MeshRenderer       →  native · generated from MBML
     ├── Rigidbody          →  native · from Preset
     └── NFCReaderFeature   →  Custom Feature · generated
                                makes the Block NFC-capable

2. Block → Custom Code directly
   no NativeBlock foundation · everything generated or hand-written
   more effort · less structured
   valid when no suitable NativeBlocks exist

3. Blocks → existing Product (Keycloak · Shopify · Stripe · ...)
   no code generated · only configuration
   the Product itself is the Render Target
   deterministic when DSL + Compiler exist
   Keycloak example: Identity Blocks → Realm configuration
```

These are not rules — they are a preference order. The first approach minimises generated code and maximises structure. The third approach is the most deterministic when applicable. The second is the fallback.

---

**Atomic Render Target**
A single, indivisible Render Target — one technology, one output:

```
SCAD     →  geometry for 3D Printer
Python   →  firmware for PiMachine
React    →  UI for Browser
JSON     →  configuration for a service
```

---

**Composite Render Target**
A Set containing multiple Block types may require multiple Atomic Render Targets simultaneously. A Composite Render Target is the combination of all Atomic outputs needed to manifest a complete Set.

```
Device Set (Martian Micro)
  ├── Housing Block    →  Atomic: MBML → SCAD      (MachineBlocks Renderer)
  ├── NFC Module       →  Atomic: DSL → Python      (MachineMania Renderer)
  ├── Speaker Block    →  Atomic: DSL → Python      (MachineMania Renderer)
  └── App Block        →  Atomic: Control → React   (ScreenMachine Renderer)

Composite Render Target: SCAD + Python + React
                          all together = one functioning Device ThingKit
```

The Manifestor (e.g. DeviceForge) acts as orchestrator for Composite Render Targets — it identifies which Block needs which Atomic Renderer, coordinates all outputs, and assembles them into a single ThingKit.

---

**Manifestor**
A role that a Thing may fulfil — not a type. A Manifestor is a Thing that produces ThingKits from Ideas and Wishes. Like Addressee, it is a role — a Thing can hold multiple roles simultaneously.

```
MetaPhone    →  Thing · Addressee · Manifestor · AccessPoint
                 three roles · one entity
                 from Actor perspective:   AccessPoint
                 from World perspective:   Manifestor (produces Launchpads)
                 as Thing:                 Addressee (has stud:// address)

BlockFoundry →  Thing · Addressee · Manifestor
IdentityThing →  Thing · Addressee · Identity role
WCMS         →  Thing · Addressee · Manifestor · WCMS role
```

A Manifestor is always an Addressee — Wishes must be able to reach it.
*FQN: world.wot.core.Manifestor*

The Manifestor does not manifest — it produces the best possible ThingKit. The full Manifestation (from Idea to Thing) includes the Runtime. The Manifestor is responsible only for the ThingKit — not for what the Runtime does with it.

```java
interface Manifestor extends Addressee {
    ThingKit create(Idea idea, Wish wish);
    ThingKit modify(Thing thing, Wish wish);
}
```

A Manifestor does not need to be an Intelligence itself — it typically uses one. The LLM thinks. The Compiler translates. The Manifestor orchestrates.

```
Manifestor can be:
  Thing          →  BlockFoundry · DeviceForge · runs in Runtime
  Actor          →  the potter · uses his own Intelligence
  uses LLM       →  to translate Wish into DSL
```

Manifestors follow one of two patterns:

```
Foundry  →  casts · reproducible · from a mold
             same input → same structure · always
             BlockFoundry · ScreenFoundry (via ScreenMachine)

Forge    →  assembles · combines parts · composes
             takes different Blocks · combines into one Thing
             MachineForge · DeviceForge · WorldForge
```

Every Manifestor has a Compiler at its disposal. The division of responsibility is strict:

```
LLM        →  translates Wish into DSL · as little code as possible
Compiler   →  translates DSL into ThingKit · deterministic
Runtime    →  executes · no interpretation
```

Exception: when the Thing itself is not deterministically describable — a poem, an image, music — the LLM output is the Manifestation directly. A poem cannot be compiled. It can only be written.

---

**ThingKit**
The output of a Manifestor. The necessary intermediate stage between Idea and Thing — the instructions, parts, and metadata that the Runtime needs to bring a Thing into existence.

A ThingKit is not the Thing. It is not the Manifestation. It is the best possible precondition — as complete as the Manifestor can make it, never perfect.

```
ThingKit
├── manifest.json   →  envelope · UUID · Actor reference · Wish reference
├── MML             →  description of what should be manifested · for Runtime
└── Deliveries[]   →  variable space · World fills freely
                        physical parts · firmware · Manual · invoice · video
                        everything is a Delivery · including the Manual
```

A ThingKit is not reusable — by definition.
*FQN: world.wot.core.ThingKit* It is bound to a specific Wish, Actor, and context. As an artefact (manifest.json · MML · Deliveries) it can be stored. But it cannot be reused for a different Actor or a different Wish — the binding is permanent. Exception: a fully digital Thing may produce a ThingKit that is both storable and reproducible, since no physical Deliveries exist.

MML contains only metadata. A Delivery can be physical, digital, or both — the World decides.

There is no Replicator. There are always manual steps — assembly, ordering, waiting, configuring. Deliveries make these steps visible and human-readable:

```
PhysicalDelivery  →  Blocks · electronics · someone must assemble
SoftwareDelivery  →  firmware · someone must deploy
OrderDelivery     →  order from supplier · someone must wait
ManualDelivery    →  instructions · always present · even if one sentence
```

---

**Runtime**
The preconditions that must be present for a Thing to exercise its Capabilities. Not a system. Not a service. Simply: what must exist or be in place.

Runtime is proportional to the Manual — the more Runtime prerequisites the Actor must fulfil, the more steps appear in the Manual.

```
Ceramic cup      →  Runtime: gravity · solid surface
                     invisible · self-evident · zero Manual steps

NFC Music Player →  Runtime: power · internet · PiMachine running
                     partially visible · some Manual steps

3D printed part  →  Runtime: 3D Printer · filament · slicer software
                     explicit · must be provided · appears as Deliveries
```

Runtime is not modelled by the WOT. Each World defines what its Things require. How visible the Runtime is determines how many gaps exist in the Manual.

```
invisible Runtime  →  self-evident prerequisites · no Manual steps
                       browser · gravity · electricity from the wall

explicit Runtime   →  prerequisites the Actor must actively provide
                       3D Printer · PiMachine · specific hardware
                       each appears as a Delivery or Manual step
```

The optimisation function points toward invisible Runtime — the Replicator is the state where all prerequisites are self-evident and the Manual has zero steps.

**AccessPoint**
The point through which an Actor enters and exits the WOT. Belongs to the Actor — not to any World. The Actor brings the AccessPoint into Worlds. Worlds are visited. The AccessPoint remains.

*Implementation: MetaPhone*

---

**Identity**
The persistent identity of an Actor in a Universe. One Identity — all Worlds accessible.

*Implementation: MakerID (Maker Universe)*

---

**WorldNet Protocol**
The WOT defines the concept of a WorldNet Protocol — the communication standard a Universe uses for all internal World-to-World messaging. Every Universe defines its own. The WOT prescribes only: there is exactly one per Universe.

A protocol is not primarily a technical specification. It is the semantic viewpoint of a Universe on a Thing — the lens through which Things are addressed and messages are routed.

```
Maker Universe   →  stud://  (its WorldNet Protocol)
SAP Universe     →  own protocol · own decision
Healthcare       →  own protocol · own decision
```

The Thing remains identical across protocols. The protocol carries the Universe perspective. Gateways translate between routing levels — not between protocols.

*Implementation in Maker Universe: stud://*

---

**Addressee TLD**
The WOT requires only: it must be possible for a Thing to have a unique address. Not every Thing must have one. Not every Thing must be reachable from everywhere. The WOT prescribes only that unique addressability is possible.

Every Universe defines its own address format and TLD. The WOT does not prescribe the format.

```
Maker Universe  →  .thing · chosen for adoption · intuitive
                    "the thing in the network"
SAP Universe    →  own TLD · own decision
```

**Maker Universe: .thing**

Managed by MakerMaker. Namespace sovereignty — no collisions possible.

```
<id>.<namespace>.thing
piblock.thing              →  namespace for PiBlock project
abs373834.piblock.thing    →  stable · hardware-bound · always reachable
```

`.thing` is the canonical fallback address. Worlds may provide readable domain aliases that map onto `.thing`.

**IdeaRepo**
A public resource outside all Universes. Reachable via the normal internet. No Universe owns it. LLM-assisted by design — Actors describe in natural language, the LLM extracts the Idea.

The IdeaRepo is rarely the starting point. The natural path is bottom-up:

```
Practice: World → Manifestation → IdeaRepo
           someone builds something · the Idea is extracted · the repo grows
```

The IdeaRepo is a knowledge graph — Ideas have relationships:

```
variant    →  same Idea · narrower ActorCustomization
similar    →  related Idea · overlapping Capabilities
derived    →  Idea B extends Idea A
```

*Implementation: thewebofthings.org (future)*

**BlockML (Block Modeling Language)**
The universal description language for Ideas. BlockML is the Maker Universe implementation of the abstract WOT concept IdeaML.

BlockML consists of two components:

```
BML  →  Block Markup Language · the language itself
         XML-based · human-readable · machine-processable
         can be written on paper · exists independently of any compiler
         SSOT — Single Source of Truth

BOM  →  Block Object Model · internal compiler representation
         produced by parsing BML · not part of the language
         like AST in a compiler pipeline · implementation detail
```

**Why XML?** XML is a conscious design decision — not a historical accident. It describes objects through named elements, expresses properties as attributes, makes hierarchies immediately visible, and allows documentation and structure to coexist. BlockML feels like a structured document, not a data container.

The translation chain:

```
Natural Language
  ↓  LLM
BML (XML)
  ↓  Parser
BOM (internal)
  ↓  Compiler
Render Target (SCAD · React · Python · ...)
  ↓  Runtime
Manifestation
```

**BlockML and OOP:** BlockML shares many concepts with OOP — Properties, Aggregations, Associations, Capabilities, Inheritance. This is not because BlockML is derived from OOP. Both independently abstract the same universal organisational principles of reality. A tree has properties. A car consists of components. A dog is a mammal. These exist without computers.

OOP formalised these patterns for software. BlockML formalises them for Ideas — universally, before any World.

> **OOP is a special case of BlockML, not the other way around.**

**BlockML positions itself between natural language and programming languages** — semantically rich enough to describe Ideas precisely, structured enough to be processed deterministically by compilers. It is the shared language of humans, LLMs, and machines.

*Namespace: org.blockml.* — all BlockML Core Blocks*
*Domain: blockml.org*

**Two BlockML formats:**

```
BML   →  a single Block definition · application/bml+xml
           exists independently · SSOT · autarkic

BMLM  →  Block Markup Language Message · multipart/bml
           a list of Blocks as a multipart message
           each Block is autarkic · together they form a context
           Blocks may reference each other · need not
```

BMLM example — an image prompt composed from multiple Idea Blocks:

```
Content-Type: multipart/bml; boundary="msg"
BMLM-Version: 1.0

--msg
Content-Type: application/bml+xml
<block type="prompt:CreateImage"> ... </block>

--msg  
Content-Type: application/bml+xml
<block type="place:AbandonedObservatory"> ... </block>

--msg
Content-Type: application/bml+xml
<block type="person:YoungAstronomer"> ... </block>
--msg--
```

The LLM reads all Blocks as a coherent context. Each `<idea>` element gives the immediate essence. `<properties>` give the details. Together they form a complete, structured prompt — without natural language ambiguity.

BMLM can also serve as: a Wish (Actor context + Idea), a ThingKit (Manifestor output), an AI Context (World knowledge for a Manifestor), or a Message between Things via stud://.

## 3 · Models

### The Ontology

```
Idea
  ↓
Universe          →  organizes the Idea
  ↓
World             →  interprets the Idea
  ↓
Manifestor        →  produces ThingKit from Idea + Wish
  ↓
ThingKit          →  intermediate stage · instructions · best possible
  ↓
Runtime           →  brings Thing into existence
  ↓
Thing             →  exists · has Capabilities · runs in the world
```

Manifestation is the entire process — from Idea to Thing. Every level is part of this process. There are no exceptions — including the WOT itself, which is a Manifestation of the Idea "a framework for making Ideas machine-readable".

### From Wish to Thing

```
Actor
  ↓
Wish                    →  what the Actor wants · structured or natural language
                            always within a World context
  ↓
World                   →  gives the Wish meaning
  ↓
Manifestor.create()     →  Idea + Wish → ThingKit
  or
Manifestor.modify()     →  Thing + Wish → ThingKit
  ↓
ThingKit                →  MML · Deliveries · metadata
  ↓
Runtime.prepare()       →  assembles Deliveries · guides Actor · dashboard
  ↓
Runtime.run()           →  Thing is live · continuous stream
  ↓
Thing                   →  exists · has Capabilities · has address (if Addressee)
```

A Thing already exists as a potential in the ThingKit before the Runtime executes it. The Runtime does not create the Thing — it activates it.

There is always a manual step between ThingKit and living Thing. Deliveries make this explicit. No Delivery completes itself.

### Three Levels of Meaning in BlockML

BlockML separates the description of a model from its interpretation. This keeps the language universal and independent of any concrete target platform.

```
Level 1: Language Semantics (BML itself)
  Block · Property · Aggregation · Association · Capability
  Inheritance · Contracts · Type system · Constraints
  renderer-independent · identical for every BlockML implementation
  "what BlockML means"

Level 2: World Semantics (Renderer)
  MachineBlocks  →  mb_block() in OpenSCAD
  React          →  JSX components
  Unity          →  GameObjects / Prefabs
  KiCad          →  schematic and PCB objects
  "how a Block looks in this World"

Level 3: Execution Semantics (Runtime)
  usually no own semantics · executes the Renderer output
  OpenSCAD interprets SCAD · React interprets JSX · 3D Printer prints
  "how the interpretation is executed"
```

BlockML describes only the Idea. The Renderer decides meaning. The Runtime executes.

### NativeBlocks (Best Practice for Render Targets)

A BlockML domain may define NativeBlocks — the smallest, indivisible semantic units of the domain. NativeBlocks are part of the domain specification (BML), not a Runtime concept. They are the building blocks every Renderer of that domain understands.

**Best Practice:** map NativeBlocks as directly as possible to native constructs of the target language. This makes the Renderer a simple emitter that mostly generates syntax.

```
BML Domain
  Wall · Frame · StandardBrick · NativeBlock · ...
    ↓
Renderer (interprets the domain)
    ↓
Target Language (OpenSCAD · React · Python · KiCad)
```

A Renderer may deviate from 1:1 mapping — optimise, combine, or translate differently. NativeBlocks provide a stable canonical foundation within the domain. Renderers remain completely free in their implementation.

### The Optimisation Function

There is no such thing as an unimportant step. Every step between Wish and living Thing is necessary. The goal is not to eliminate steps — it is to eliminate gaps.

> A gap is a step the Actor must figure out alone. Gaps are UX failures. Steps are not.

LEGO proves this works. A large LEGO set is highly complex — yet anyone can build it. Because every step has the same dignity. No step is "obvious." No gap. No prior knowledge assumed.

The WOT applies this to everything — software installation, physical assembly, waiting for delivery, configuring a device. All the same. All explicit. All visible.

```
today          →  many steps · some gaps
tomorrow       →  fewer steps · no gaps · new technology closes one gap
Replicator     →  zero steps · zero gaps · the asymptotic limit
```

Every new technology is an opportunity to close one gap:

```
3D Printer          →  closes "order housing · wait weeks"
Mini-LLM on chip    →  closes "formulate Wish in structured form"
Autonomous robotics →  closes "assemble by hand"
```

Martian Micro's mission: close gaps between Wish and Thing.

### Manifestor Evolution

The Manifestor architecture is deliberately evolutionary. LLMs and deterministic Compilers are not opposites — they are different tools within the same architecture, applied at different stages of World maturity.

**Phase 1 — New World**
A new World has few formalised rules. The Manifestor uses LLMs to interpret Ideas into BML and to produce early Manifestations.

```
Idea → LLM → BML → LLM → Manifestation
```

Speed, exploration, and learning are the priority.

**Phase 2 — Consolidation**
Stable Block Libraries, type systems, and recurring patterns emerge. These are progressively formalised. More of the Manifestation becomes deterministic.

```
Idea → LLM → BML → Compiler + Templates + LLM → Manifestation
```

**Phase 3 — Mature World**
The language of the World is largely understood. The Manifestor uses LLMs mainly for Idea interpretation. Manifestation is mostly deterministic.

```
Idea → LLM / Rules / Human → BML → Compiler → Manifestation
```

The Manifestation is now reproducible · testable · versionable · cacheable · optimisable.

**The long-term direction:**

```
LLM → Recognition → BML Model → Deterministic Rules → Compiler
```

Knowledge migrates continuously from probabilistic LLM interpretations into formalised BML models and finally into deterministic Compiler logic. The LLM does not disappear — its role shifts from generating Manifestations to generating BML.

```
Interpretation (Idea → BML)   →  may be creative and probabilistic
Manifestation  (BML → output) →  should be as deterministic as possible
```

Every World that produces deterministic Things defines three components:

```

               the contract between LLM and Compiler

               same DSL → same output · always

```

### Universe Roles

The WOT prescribes that certain roles must exist within a Universe for communication to be possible. Any World can fulfil these roles — there is no master World, no Universe infrastructure.

```
Identity Provider  →  Actors can be recognised and authenticated
                       can be centralised (MakerID in Maker Universe)
                       can be decentralised (each World has own Identity)
                       can be bilateral (World A accepts World B's identity)
                       can use IdP federation (translate between identities)

Router             →  Messages can be routed between Things and Worlds
                       can be centralised (MakerMaker in Maker Universe)
                       can be decentralised (peer-to-peer routing)

AccessPoint        →  Actors can enter the Universe and send Messages
                       MetaPhone is one Manifestation · not a WOT necessity
```

The WOT does not prescribe how many Identity Providers exist, or whether routing is centralised. The Maker Universe has chosen: one central MakerID, routing via MakerMaker. This is a Maker Universe decision — not a WOT rule.

When a World sends a message to another World, the receiving World must accept the sender's identity authority — either bilaterally, through a shared central Identity Provider, or through IdP federation.

World Repositories belong to the Worlds. MakerStore and MakerToken are a monetisation layer — not Universe roles.

### MachineBlocks

**Type:** Physical World · vertical · Implementation
**Manifestor:** BlockFoundry
**Runtime:** 3D Printer
**Namespace:** piblock.thing (for PiBlock project)
**Exports:** Blocks (Brick · Plate · Tile · Connector · Channel)

**Repository:** Blockiverse

MachineBlocks is the most complete approximation of the WOT in a single project. Every WOT concept has a direct MachineBlocks equivalent — not by design, but by consequence.

**MachineMania Block Types**

MachineMania defines two fundamental base types for Electronic Blocks:

```
ComputeBlock     →  the host · has its own processing capacity
                     executes Firmware · is the Runtime for Modules
                     has IP address · is Addressee · stud:// capable
                     Examples: PiBlock · ArduinoBlock · ESP32Block

ModuleBlock      →  the peripheral · no own processor
                     attached to a ComputeBlock · executed by it
                     has no own stud:// address
                     addressed via its ComputeBlock
                     Examples: NFCBlock · SpeakerBlock · LEDBlock
```

The Firmware of a ModuleBlock is a ServiceBlock — it runs on the ComputeBlock, not on the Module itself:

```
NFCBlock (ModuleBlock)
  ├── Properties:    boardType: PN532 · connection: I2C · address: 0x24
  ├── Capabilities:  nfcTagRead (inbound) · tagDetected (outbound)
  └── FirmwareBlock  →  ServiceBlock · Dedicated Renderer
                         runs on ComputeBlock · not on NFCBlock
                         NFCBlock has no processor

stud://pi-123.piblock.thing/nfc/tagRead
  →  pi-123  =  ComputeBlock (PiBlock)
     nfc      =  ModuleBlock namespace
     tagRead  =  Capability
```

The Preset decides which board and which Renderer:

```
NFCBlock Preset: pn532-raspberry-pi
  boardType:   PN532
  connection:  I2C
  firmware:    pn532-pi-renderer  →  which RendererSet for the Firmware
  renderTarget: PiMachine
```

A ComputeBlock always comes first. ModuleBlocks attach to it. The ComputeBlock is the Runtime for all its Modules.

The **PiBlock** is the clearest example of World cooperation in one object:

```
PiBlock   →  a MachineBlocks Block · Block is primary
              contains a PiMachine (MachineMania Runtime) inside
              MB provides: form · Stud · physical structure
              MachineMania provides: Runtime · intelligence · connection
```

PiBlock, not BlockPi — because the Block is the unit. The Pi is what is inside it.

BlockFoundry uses the MBML Compiler as a tool — the Compiler is not the Manifestor. BlockFoundry thinks. The Compiler translates. The 3D Printer executes.

```
BlockFoundry (Manifestor)
  ↓
MBML Compiler  →  MBML → SCAD
  ↓
3D Printer (Runtime)  →  SCAD → physical parts
```

MachineBlocks may operate more than one Foundry. Currently: one BlockFoundry handling both physical and electronics manifestation. Electronics are delegated internally to MachineMania — Martian Micro never speaks to MachineMania directly.

MBML was developed by MachineBlocks and contributed to the Maker Universe — like open source: the origin is acknowledged, the usage is open. MBML is now Maker Universe infrastructure, usable by any World within it.

MBML is a BOM dialect with its own:
```
BaseTypes    →  com.machineblocks.core.Block
Types        →  com.machineblocks.types.Size3D · Direction · Color · ...
Block Library →  Brick · Plate · Tile · Connector · Channel · ...
```

MBML is not a WOT standard — other Universes may use other physical DSLs. It is a Maker Universe standard because MachineBlocks contributed it. Like HTML: developed by browser vendors, contributed, became the web standard.

The MB NFC Player is a MachineBlocks Set: large, experimental, open. The Maker builds it themselves. The electronics are visible. The process is part of the product. It is not a consumer device — it is a Maker object.

### Hello, World I: the Burger

The burger is the WOT's Hello, World — simple enough that everyone understands it, rich enough to show everything.

A burger is an Idea. It has no calories, no taste, no material. It becomes something only when a World interprets it.

**AppWorld / ScreenMachine** — the configurator: the Actor sees a BurgerConfigurator App. Interactive. Digital. Delivery: running App.

**MachineBlocks** — the physical model: the Actor receives physical parts. Assembled by hand. A Maker object — not food.

**McDonald's World** *(illustration)* — the food: the Actor receives a meal. Edible. A commercial food reality.

**Martian Micro** — the production plant:

```
DeviceForge (MM Manifestor)
  ↓
Set: BurgerProductionPlant
  Block: DoughDevice     →  manifested by BlockFoundry (MB)
  Block: GrillDevice     →  manifested by BlockFoundry (MB)
  Block: AssemblyDevice  →  manifested by BlockFoundry (MB)
```

Martian Micro does not manifest burgers. It manifests what manifests burgers.

**MachineMania** — two interpretations:

```
A: Burger Automat  →  Device that makes burgers
B: PCB Layout      →  Burger = layers in order · PCB = layers in order
                        Bun top → Ground Plane · Patty → Main chip
```

Nobody planned interpretation B. The Idea was abstract enough. The World was creative enough.

**Gedichte World** *(illustration)* — language as sound: the burger becomes a poem. The Runtime is the reader's imagination.

---

The Idea did not change. The World changed everything.

> A World never rejects an Idea. It finds its own interpretation.

### The Ancient Potter

A customer wants a vessel for warm liquids — with a handle, dark brown. The Gateway is a piece of paper:

```
┌─────────────────────────────────┐
│ Order #042                      │
│ Idea: vessel                    │
│ Wish: for warm liquids          │
│       with handle · dark brown  │
└─────────────────────────────────┘
```

The potter is the Manifestor. He takes the Idea and the Wish and produces a vessel. The shelf is the Runtime — not a computer. A shelf.

```
Runtime.prepare(vessel)  →  vessel placed on shelf · ready
Runtime.run(vessel)      →  vessel holds water · Capability active
```

**The Carrier Pigeon Gateway**

What if the Wish comes from a digital World — and the potter has no computer?

```
Digital World   →  stud:// Message
  ↓  Gateway: Carrier Pigeon → printed note → pigeon
Ancient World   →  potter reads note · manifests vessel
  ↓  Gateway back: pigeon with reply note
Digital World   →  "vessel ready · market · stall 7"
```

In the ancient world, the carrier pigeon is the only remote communication instance — alongside the messenger boy. These are the Gateways of the ancient World. Not metaphor. Technical reality.

```
Carrier pigeon  →  Thing · Gateway · Addressee · address: dovecote 3
Messenger boy   →  Delivery · carries physical Things · step in the Manual
```

The WOT does not invent Gateway. It names what has always existed.

The optimisation function across centuries:

```
ancient   →  messenger boy carries vessel
today     →  DHL delivers package
future    →  autonomous drone
Replicator →  no delivery · Thing manifests at destination
```

### Amazon — Old World Commerce

Amazon today: one operator, one system. A Wish enters — Amazon handles everything. No other World participates. The ceiling is Amazon's ceiling.

In the WOT: the same Wish cascades through multiple Worlds:

```
Actor Wish
  ↓
Commerce World  →  interprets · finds best source
  ↓
Supplier World  →  provides the Thing
  ↓
Logistics World →  handles delivery
  ↓
Payment World   →  handles transaction
```

Each World contributes what it does best. Any World can be replaced without touching the others. This is not better Amazon — it is a structurally different model.
